Your agent doesn't know your design system. It knows the average of the internet.

I ran into this myself. We wrote skills and rules, but never linked them together or tied skills to roles. The agent built look-alikes instead of using our components. They looked plausible, but the agent made them up.

So the question is: where should design rules live so an agent actually reads them? One current answer is DESIGN.md. Here is what it is, what we know about it, and where it stops.

Where it came from

DESIGN.md started in Google Stitch. On March 18, 2026, Google announced "vibe design" in Stitch along with DESIGN.md. It's a markdown file for agents: you export design rules from Stitch with it and import them into other design and code tools.

On April 21, Google open-sourced a draft spec. The idea: an agent doesn't have to guess what a color is for. It can know it and check its choices against WCAG. The spec lives on GitHub at google-labs-code/design.md under Apache 2.0. It's marked alpha, and the authors warn it will change. As of October 28 the repo has about 28.6k stars.

How it works

The file has two layers:

  • YAML tokens hold the exact values: colors, typography, radii, spacing, components
  • Markdown prose explains why those values exist and how to apply them

Tokens can reference each other, like {colors.primary}. The format builds on W3C Design Tokens. The authors say tokens convert easily to and from tokens.json, Figma variables and Tailwind themes.

Sections go in this order: Overview, Colors, Typography, Layout, Elevation & Depth, Shapes, Components, Do's and Don'ts. The last one is my favorite: I recommend do/don't examples for every component anyway.

There's a linter: npx @google/design.md lint DESIGN.md. It catches broken references, cycles and bad values, and checks WCAG contrast. A diff command compares versions.

Vercel, Atlassian, Ant Design and Microsoft FAST already publish their own DESIGN.md. There are big community collections too, but most are reconstructions scraped from brand websites. Good for studying structure, not for copying.

What it can't do

A component in the spec has few properties: background color, text color, typography, radius, padding and size. States like hover are separate entries.

Behavior, accessibility and how components fit together don't fit into tokens. You can only describe them in prose. And that's exactly where my agent went wrong: it built look-alikes instead of using our components.

That's why to me a design system is design, docs and code together. DESIGN.md covers how the product looks. Other tools tell the agent more about real components:

  • Figma MCP returns the structure of the selected frame plus variables: color, spacing, type
  • Code Connect adds the import and snippet for your actual component. Figma calls it the most effective way to get an agent to reuse your components
  • At Config India on October 15, Figma showed Guidelines (open beta) and Code sources (closed beta as of October 28): rules inside published libraries, and code imported from GitHub or npm

Who reads it

I found no confirmation that any agent other than Stitch reads DESIGN.md on its own. Neither agents.md nor the Cursor and Claude Code docs mention it.

AGENTS.md is different. OpenAI released it for Codex in 2025 and moved it to the Agentic AI Foundation under the Linux Foundation on December 9, 2025. Codex, Cursor, GitHub Copilot, Gemini CLI and others read it. The agents.md site says over 60,000 open-source projects use it.

So you wire DESIGN.md in by hand: link it from AGENTS.md or CLAUDE.md, or put it in the prompt. AGENTS.md tells the agent how to build the project. DESIGN.md tells it what the result should look like.

What the data says

I found no measurement of DESIGN.md's effect. Stitch says a design system greatly improves consistency, but that's marketing: there's no data behind it.

The only numbers are for AGENTS.md, and they're sobering:

  • January, arXiv (10 repos, 124 PRs): with AGENTS.md, median run time dropped 28.6% and the success rate stayed comparable
  • February: model-written context files didn't raise success and made runs 20-23% more expensive. Developer-written ones gave +2.4%, not statistically significant
  • July, on Claude Code and Codex: no effect on correctness, though the authors admit the sample is small

So these files save the agent time but don't make it smarter. DESIGN.md is probably the same, but nobody has measured it yet.

How to start

  • Write it by hand and keep it short. Per the data, generated files don't help and make runs more expensive
  • Include only what the agent can't guess: your own decisions
  • Give a do/don't example for every component
  • Run the linter: it checks contrast for free
  • Link DESIGN.md from AGENTS.md, most agents won't find it on their own
  • Feed real components through code and Figma MCP, not screenshots

For live examples, see Vercel's and Atlassian's files.

DESIGN.md explains to an agent how your product looks. But building it from your components is still something the code teaches.
