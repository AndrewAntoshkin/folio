DESIGN.md: как объяснить агенту, как выглядит ваш продукт

DESIGN.mdAGENTS.mdagents

Что такое DESIGN.md от Google, чем он отличается от AGENTS.md и чего от него пока не ждать.

28 октября 20264 мин

Ваш агент не знает вашу дизайн-систему. Он знает среднее по интернету.

Я столкнулся с этим сам. Мы написали скиллы и правила, но не связали их между собой и не привязали скиллы к ролям. Агент собирал похожие компоненты вместо наших: выглядело правдоподобно, но это была его выдумка.

Отсюда вопрос: где хранить правила дизайна, чтобы агент их прочитал? Один из ответов сейчас DESIGN.md. Разберу, что это за файл, что о нём известно и где его границы.

Откуда он взялся

DESIGN.md появился в Google Stitch. 18 марта 2026 Google анонсировал в Stitch «vibe design» и вместе с ним DESIGN.md. Это markdown-файл для агентов: через него правила дизайна выгружают из Stitch и загружают в другие инструменты для дизайна и кода.

21 апреля Google открыл черновик спецификации. Идея анонса: агенту не нужно угадывать, зачем нужен цвет. Он может это знать и проверять свой выбор по WCAG. Спецификация лежит на GitHub в google-labs-code/design.md под лицензией Apache 2.0. Статус формата alpha, авторы предупреждают, что он будет меняться. На 28 октября у репозитория около 28,6 тысячи звёзд.

Как он устроен

В файле два слоя:

  • YAML-токены задают точные значения: цвета, типографику, скругления, отступы, компоненты
  • Текст в markdown объясняет, зачем эти значения и как их применять

Токены могут ссылаться друг на друга, например {colors.primary}. Формат опирается на W3C Design Tokens. По словам авторов, токены легко переводятся в tokens.json, переменные Figma и тему Tailwind и обратно.

Разделы идут в таком порядке: Overview, Colors, Typography, Layout, Elevation & Depth, Shapes, Components, Do's and Don'ts. Последний мне ближе всего: примеры «так делай, так не делай» для каждого компонента я и сам советую писать.

Есть линтер: npx @google/design.md lint DESIGN.md. Он ловит битые ссылки, циклы и неверные значения, проверяет контраст по WCAG. Команда diff сравнивает версии файла.

Свои DESIGN.md уже выложили Vercel, Atlassian, Ant Design и Microsoft FAST. Есть и большие подборки от сообщества, но там в основном реконструкции чужих дизайн-систем, собранные с сайтов брендов. Структуру подсмотреть полезно, копировать не стоит.

Чего он не умеет

У компонента в спецификации мало свойств: цвет фона, цвет текста, типографика, скругление, внутренние отступы и размеры. Состояния вроде hover описываются отдельными записями.

Поведение, доступность и то, как компоненты собираются вместе, в токены не ложатся. Их можно описать только текстом. А как раз здесь агент у меня и ошибался: собирал похожие компоненты вместо наших.

Поэтому для меня дизайн-система это дизайн, документация и код вместе. DESIGN.md отвечает за то, как продукт выглядит. Про реальные компоненты агенту лучше расскажут другие инструменты:

  • Figma MCP отдаёт структуру выделенного фрейма и переменные: цвета, отступы, типографику
  • Code Connect добавляет импорт и сниппет вашего настоящего компонента. Figma называет его самым надёжным способом заставить агента переиспользовать ваши компоненты
  • 15 октября на Config India Figma показала Guidelines (открытая бета) и Code sources (на 28 октября закрытая бета): правила прямо в опубликованных библиотеках и импорт кода из GitHub или npm

Кто его читает

Подтверждения, что DESIGN.md сам читает какой-то агент, кроме Stitch, я не нашёл. Ни agents.md, ни документация Cursor и Claude Code его не упоминают.

С AGENTS.md иначе. OpenAI выпустил его в 2025 году для Codex, а 9 декабря 2025 передал в Agentic AI Foundation при Linux Foundation. Его читают Codex, Cursor, GitHub Copilot, Gemini CLI и другие. По данным сайта agents.md, формат используют больше 60 тысяч open-source проектов.

Поэтому DESIGN.md подключают вручную: ссылкой из AGENTS.md или CLAUDE.md либо прямо в промпте. AGENTS.md говорит агенту, как собирать проект, DESIGN.md говорит, как результат должен выглядеть.

Что говорят данные

Замеров эффекта от DESIGN.md я не нашёл. Stitch пишет, что дизайн-система сильно улучшает консистентность, но это маркетинг: данных за фразой нет.

Замеры есть только для AGENTS.md, и они отрезвляют:

  • Январское исследование на arXiv (10 репозиториев, 124 PR): с AGENTS.md медианное время работы ниже на 28,6%, доля решённых задач сопоставима
  • Февральское: контекст-файлы, написанные моделью, не подняли успех, но сделали работу дороже на 20-23%. Файлы, написанные разработчиком, дали +2,4%, это статистически незначимо
  • Июльское, на Claude Code и Codex: эффекта на корректность нет, хотя авторы признают, что выборка мала

Выходит, такой файл экономит агенту время, но умнее его не делает. Скорее всего, с DESIGN.md так же, но проверенных цифр пока нет.

Как начать

  • Пишите файл руками и коротко. Сгенерированный моделью, судя по данным, не помогает и делает работу дороже
  • Кладите туда только то, чего агент не угадает: ваши собственные решения
  • Для каждого компонента дайте пример «так / не так»
  • Прогоните линтер: контраст он проверит бесплатно
  • Сошлитесь на DESIGN.md из AGENTS.md, сам агент его, скорее всего, не найдёт
  • Реальные компоненты отдавайте через код и Figma MCP, а не скриншотами

Живые примеры смотрите в файлах Vercel и Atlassian.

DESIGN.md хорошо объясняет агенту, как выглядит ваш продукт. Но собирать продукт из ваших компонентов его всё равно учит код.
